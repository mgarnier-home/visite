# Visite — intégration continue

Date : 2026-10-25
Statut : en relecture

## 1. Objet

Deux workflows GitHub Actions pour le dépôt `mgarnier-home/visite` :

- **Tests** : lancer toute la suite sur chaque pull request vers `main` et sur chaque push sur
  `main` ;
- **Publication** : construire et publier l'image Docker multi-architecture quand un tag
  `vX.Y.Z` est poussé.

Ils reprennent les conventions des dépôts existants : `potixx` pour les tests (runners GitHub,
navigateurs Playwright installés avec leurs dépendances), `orchestrator-cli` pour la publication
(runners auto-hébergés par architecture, fusion multi-arch, cache sur le registre du homelab).

## 2. Workflow « Tests » (`.github/workflows/test.yml`)

- Déclencheurs : `pull_request` vers `main`, `push` sur `main`.
- `concurrency` : groupe `${{ github.workflow }}-${{ github.ref }}`, exécution en cours annulée par
  un nouveau push. `permissions: contents: read`.
- Runners : `ubuntu-latest` (GitHub).
- Trois jobs en parallèle :
  - **Back** : Go installé par `actions/setup-go` depuis `backend/go.mod` (Go 1.26.4) ;
    `go vet ./...` puis `go test -race ./...` dans `backend/`.
  - **Front** : Node installé par `actions/setup-node` depuis `.tool-versions` (24.16.0), cache
    npm sur `frontend/package-lock.json` ; `npm ci`, `npx ng test --watch=false`, `npx ng build`
    dans `frontend/`.
  - **Bout en bout** : Go, Node et `task` installés ; `npm ci` ;
    `npx playwright install --with-deps chromium` ; `task e2e` (construit le front et le back,
    lance les scénarios Playwright). En cas d'échec, `frontend/playwright-report/` et
    `frontend/test-results/` sont archivés 7 jours.
- Libellés des étapes en français, comme dans `potixx`.

## 3. Workflow « Publication » (`.github/workflows/publish.yml`)

- Déclencheur : `push` d'un tag `v*.*.*`. Le premier job vérifie le nom du tag avec
  `^v[0-9]+\.[0-9]+\.[0-9]+$` (passé par variable d'environnement, jamais interpolé dans le
  script) et en tire la version `X.Y.Z` (sans `v`).
- `concurrency` : groupe par tag, sans annulation (une publication interrompue laisserait des
  tags à moitié poussés).
- Construction : un job par architecture, sur le runner auto-hébergé `linux/amd64` puis
  `linux/arm64`, `docker buildx build --push` du `Dockerfile` existant avec :
  - le tag `mgarnier11/visite:<arch>` ;
  - les arguments `VERSION=vX.Y.Z`, `COMMIT=${{ github.sha }}`, `DATE=<UTC ISO 8601>` (le binaire
    renvoie alors `vX.Y.Z` sur `/version`) ;
  - le cache `registry.mgarnier11.fr/visite:buildcache-<arch>` (`mode=max`).
- Fusion : job sur `linux/amd64`, `docker buildx imagetools create` des deux images vers
  `mgarnier11/visite:X.Y.Z` et `mgarnier11/visite:latest`.
- Authentification : celle déjà présente sur les runners auto-hébergés (aucun nouveau secret).
  Le dépôt `mgarnier11/visite` doit exister sur Docker Hub (à la charge du propriétaire).

## 4. Hors périmètre

Déploiement (compose dans `orchestrator`), release GitHub, notifications ntfy, règles de
protection de branche (le propriétaire peut rendre « Tests » obligatoire dans GitHub).

## 5. Vérification

Les workflows ne peuvent pas être exécutés localement sans GitHub. Vérifications locales :
validation de la syntaxe (`actionlint` si disponible, sinon lecture), exécution à la main des
commandes de chaque job sur la VM (suite back, suite front, `task e2e`, `docker buildx build`
amd64 avec les mêmes arguments, sans `--push`). La première exécution réelle a lieu à
l'ouverture d'une PR et au premier tag.
